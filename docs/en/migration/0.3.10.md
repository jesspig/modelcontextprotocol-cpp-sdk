# 0.3.10 Release Notes

> **Status**: 0.3.10 released. `mcp::kSdkVersion` in `include/mcp/McpVersion.hpp` is `"0.3.10"`, and every signature, field, and default value on this page was checked against the final public headers under `include/mcp/`. The release delivers three groups of capabilities — processes, sessions, and cancellation: the public process API (`Spawn`), `RequestContext::SessionId()`, the session arguments of `McpServer::Elicit`/`ElicitUrl`, and the request handle with the discriminated cancellation/error model. All breaks and limits introduced by this release are listed in the "Limits" section below.

0.3.10 is a **patch** release. The 0.x series does not promise cross-version source compatibility. This release does not restore fields removed in 0.3.9 and does not add compatibility shims. The 0.3.9 migration items remain in effect; read the [0.3.9 migration guide](0.3.9.md) before upgrading.

## New API

### Process lifecycle (public process API)

New `SpawnOptions`, `SpawnedProcess`, and `Spawn`:

```cpp
struct SpawnOptions {
    std::string command;
    std::vector<std::string> arguments;
    std::string working_directory;
    std::map<std::string, std::string> environment;
    bool inherit_environment = true;
    std::string stdout_path;
    std::string stderr_path;
    bool detached = false;
};

class SpawnedProcess {
public:
    virtual ~SpawnedProcess() = default;
    virtual int64_t Pid() const = 0;
    virtual bool IsRunning() const = 0;
    virtual bool Wait(int timeout_ms) = 0;
    virtual std::optional<int> ExitCode() const = 0;
    virtual bool Terminate(int grace_ms) = 0;
};

std::unique_ptr<SpawnedProcess> Spawn(const SpawnOptions& options);
```

- With `inherit_environment=true`, `environment` overrides or appends to the parent environment; with `false`, only that map is used.
- An empty `stdout_path` / `stderr_path` means inherit or use the pipe default; a non-empty path creates or truncates the target file.
- `Wait` returns `true` when the process has exited and `false` on timeout; read the exit code with `ExitCode()`.
- `Terminate` first requests a graceful stop and force-kills after the grace period. Windows uses a Job Object to end the process tree; POSIX uses a process group and reaps children to avoid zombies.
- Arguments are not passed through a shell.
- The stdio transport does **not** call the public `Spawn` from this section: `src/transport/StdioClientTransport.cpp` starts child processes through the internal `mcp::detail::CreateProcess` (`include/mcp/transport/detail/PlatformIO.hpp`). Both paths share the low-level platform helpers `src/process/detail/PosixProcessSupport.hpp` and `WindowsProcessSupport.hpp`, but the public `mcp::Spawn` has no caller in this release's production code — only `tests/unit/ProcessTests.cpp` and `tests/unit/ProcessTestHelper.cpp` use it.

### Session context

New `RequestContext::SessionId()`:

```cpp
template <typename TParams>
class RequestContext {
public:
    std::string_view SessionId() const;
};
```

Semantics:

| Transport | Return value |
| --- | --- |
| stateful Streamable HTTP | The `mcp-session-id` for the current request; stable within a session, different across sessions |
| stdio | Empty string |
| stateless HTTP | Empty string |

Multi-session support uses one transport/server session per session, with the HTTP layer routing by `mcp-session-id`. `RequestContext` holds a `std::string` copy and never references a concurrently rewritten global session id. `McpServer::SessionId()` has existed since 0.3.9 and identifies the server instance; it is not the MCP session id.

### Elicitation session targeting

`McpServer::Elicit` and `McpServer::ElicitUrl` gained a trailing `session_id` argument (0.3.9 had no such argument on either method):

```cpp
std::future<ElicitResult> Elicit(const ElicitRequestParams& params,
    std::string_view session_id = {});
std::future<ElicitResult> ElicitUrl(const std::string& url,
    const std::string& message,
    std::chrono::seconds timeout = std::chrono::seconds(600),
    std::string_view session_id = {});
```

- Purpose: before sending an elicitation the server must resolve the client capabilities and the negotiated protocol version of the target session — with stateful Streamable HTTP and several sessions, the capabilities and negotiated version reported by `initialize` are stored only in the per-`mcp-session-id` table, and the global members are written only when the session id is empty (stdio/stateless), so omitting `session_id` cannot reach the target session's elicitation capability.
- Fallback order when `session_id` is empty: the explicitly passed session > the global entry when global capabilities already exist > the single non-empty session in the table when there is exactly one > otherwise the global entry.
- `Elicit` has no timeout argument: it waits for `ServerOptions::input_required_config->round_timeout`, falling back to the internal 600s default when that config is absent; `ElicitUrl`'s `timeout` defaults to `std::chrono::seconds(600)`.
- When the negotiated version is modern (`>= "2026-07-28"`), neither method sends the elicitation request directly; both produce `input_required` and let MRTR continue the round.

### Request handle, cancellation, and error model

New `RequestHandle`, `CancelToken`, and `IRequestCanceller`; the discriminated `RequestOutcome` reuses the definition that already existed in 0.3.9:

```cpp
using RequestOutcome = std::variant<JsonValue, ErrorData>;

struct RequestHandle {
    RequestId id;
    std::future<RequestOutcome> future;
    RequestHandle(RequestHandle&&) noexcept = default;
    RequestHandle(const RequestHandle&) = delete;
    void Cancel(std::string_view reason = {});
};

struct RequestOptions {
    std::optional<JsonValue> meta;
    std::optional<int64_t> read_timeout_ms;
    std::optional<JsonValue> input_responses;
    std::optional<std::string> request_state;
    std::function<void(const ProgressNotificationParams&)> on_progress;
    std::chrono::milliseconds timeout{kDefaultRequestTimeout};
    bool cancel_on_timeout{true};
    CancelToken cancel_token;
};

RequestHandle SendRequest(
    std::string_view method,
    JsonValue params,
    const RequestOptions& options);

std::future<JsonValue> SendRequest(
    std::string_view method,
    JsonValue params,
    const RequestMeta& meta = {},
    std::chrono::milliseconds timeout = kDefaultRequestTimeout);

std::future<JsonValue> SendRequestRaw(
    std::string_view method,
    JsonValue params,
    const RequestMeta& meta = {},
    std::chrono::milliseconds timeout = kDefaultRequestTimeout);
```

- `RequestHandle` carries the request id, the result future, and the cancellation entry point, so callers do not need to infer the id; it is move-only — the copy constructor and copy assignment are deleted.
- `CancelRequest(const RequestId&, std::string_view reason = {})` remains as the advanced cancel-by-id entry point.
- `RequestOptions` has 8 fields: `meta`, `read_timeout_ms`, `input_responses`, `request_state`, and `on_progress` carried over from 0.3.9, plus `timeout` (default `kDefaultRequestTimeout`, i.e. 60000ms), `cancel_on_timeout` (default `true`), and `cancel_token`, all three added in this release.
- `cancel_on_timeout` defaults to `true`. stdio/legacy sends `notifications/cancelled`; on a modern version, a transport that implements `IRequestCanceller` aborts that request's SSE stream through the interface. `IRequestCanceller` is a separate interface and does not change the `ITransport` vtable.
- `RequestHandle::future` returns `std::future<RequestOutcome>`; callers explicitly distinguish `JsonValue` from `ErrorData`. `SendRequestRaw` keeps the raw JSON contract and delivers errors as `{"code","message"}` (optionally with `data`).
- High-level `CallTool` / `ListTools` continue to throw `McpError`; one entry point no longer mixes error JSON with exceptions.
- The 0.3.9 `McpClient::SendRequest` had only the `std::future<JsonValue>` overload. This release keeps that overload (it forwards to `SendRequestRaw`, which is new here) and adds the overload returning `RequestHandle`.
- The `RequestHandle` overload has **no default arguments**: `method`, `params`, and `options` must all be supplied. The two-argument form `SendRequest(method, params)` still resolves to the `std::future<JsonValue>` overload, whose behavior matches 0.3.9.

### Compatibility smoke (internal build target)

New `mcp-compat-smoke` build target:

```bash
cmake --build --preset debug --target mcp-compat-smoke
```

It compiles the previous public API usage in `tests/compat/previous_public_api.cpp` and allows known breaks listed in `tests/compat/expected_breaks.txt` (that allowlist currently records the 0.3.8 → 0.3.9 breaks; this release added no entries). The baseline translation unit must compile, known breaks must fail, and any compile failure outside the allowlist fails the target. It also runs runtime checks for `FileRef` strict deserialization and the required `ResourceLink::name` (performed by the `mcp-compat-runtime` executable, which `mcp-compat-smoke` builds and invokes). The target is not registered with ctest and does not change the existing test-target count.

## Behavior fixes

- **Cancellation semantics**: timeouts and explicit cancellation end the wait promptly. stdio/legacy uses `notifications/cancelled`; modern HTTP closes the corresponding request stream. Callers should treat cancellation as eventually consistent and must not assume the cancel lands before the response.
- **Error model**: request results and protocol errors are discriminated in `RequestOutcome`; the raw entry point keeps JSON error objects, while high-level entry points keep throwing `McpError`, so one entry point no longer mixes two error shapes.
- **Session isolation**: stateful HTTP creates an independent session context per `mcp-session-id`; task owners are bound to sessions, and tasks from another session cannot be listed, read, or cancelled. stdio/stateless sessions return an empty string.
- **Process lifecycle**: `Spawn` does not go through a shell; Windows uses a Job Object to end the process tree, and POSIX uses a process group plus `waitpid` reaping. `Terminate` stops gracefully before force-killing, and `Wait` has a timeout.
- **0.3.9 fixes retained**: `ResourceLink` field validation, strict `FileRef` int64 handling, URL elicitation three-state behavior, default automatic MRTR, and authorization-context cache partitioning are unchanged.

## Limits

- **No restoration of 0.3.9 removed fields**: `ClientOptions::enable_apps_extension`, `ServerOptions::InputRequiredConfig::legacy_shim`, `ServerOptions::enable_dpop`, and `ServerOptions::enable_interceptor_alias` stay removed.
- **No old void URL handler overload**: only the deprecated `SetLegacyUrlElicitationHandler` remains; it fixes `accept` and does not expose the three-state result.
- **No compatibility shims**: the 0.x series does not promise cross-version source compatibility; 0.3.10 may still contain breaks, and every break must be documented here and in the 0.3.9 migration guide.
- **`FileRef` is strict**: fractional, NaN, infinite, out-of-range, and non-numeric values throw `DeserializeFailed`; there is no fallback to 0 or truncation.
- **`ResourceLink::name` is required**: a missing or empty `name` throws `InvalidParams` during serialization and deserialization.
- **Modern cancellation depends on `IRequestCanceller`**: only a transport implementing that interface gets request-scoped aborts (the built-in `StreamableHttpClientTransport` does); otherwise both modern and legacy fall back to `notifications/cancelled`. The local wait still ends promptly with `RequestCancelled` (explicit cancel) or `RequestTimeout` (timeout), but the peer's in-flight request stream is not interrupted.
- **Undeclared capability scope is unchanged**: full sampling, Apps UI rendering, jwt-bearer authorization, and the other items in the README's unsupported declarations remain out of scope; this release does not widen those promises.

## Upgrading from 0.3.9

1. Apply the [0.3.9 migration guide](0.3.9.md) field and signature replacements.
2. Call `SendRequest(method, params, options)` (all three arguments required) when you need the handle and the discriminated outcome; the `std::future<JsonValue>` overload is unchanged and can still be used, or replaced with `SendRequestRaw`, which is new in this release.
3. Configure process startup through `SpawnOptions`; do not concatenate commands into a shell string.
4. Server code that needs session isolation should read `RequestContext::SessionId()` instead of relying on global state.
5. Run the compatibility smoke and the full test suite:

```bash
cmake --preset debug
cmake --build --preset debug --target mcp-compat-smoke
cmake --build --preset debug
ctest --preset debug --output-on-failure
```
