# 扩展

扩展是协议能力的可选叠加层：它在能力表里占一个键，在线路上占一组方法，在实现里占一个开关。本页说明开关族与协议扩展标识的对应关系、能力推导结果，以及开关关闭时入口的行为差异。类型与字段表见 [/zh/reference/auth-and-extensions](/zh/reference/auth-and-extensions)。

## 扩展如何在协议里出现

能力结构里与扩展相关的只有一个映射：把反向 DNS 形式的标识符映射到该扩展的配置对象（自由格式 JSON）。服务端能力由注册与开关推导，客户端能力由选项推导，两端都用同一个映射协商。方法名本身不藏在扩展里——扩展要么带来自己的方法，要么改变已有方法的行为，具体归属见 [/zh/learn/protocol-versions](/zh/learn/protocol-versions)。

## 只有四个开关会落到线上

八个服务端开关里，只有四个会在能力表里写下扩展键：

| 线上标识 | 服务端开关 | 声明条件 | 声明值 |
|---------|-----------|---------|--------|
| `io.modelcontextprotocol/tasks` | `enable_tasks_extension` | 开关为真即声明 | 空设置对象 |
| `io.modelcontextprotocol/skills` | `enable_skills_extension` | 开关为真**且**至少注册一个技能**且**已具备资源能力 | 设置对象，含目录读取标记 |
| `io.modelcontextprotocol/ui` | `enable_apps_extension` | 开关为真即声明 | 空对象 |
| `io.modelcontextprotocol/server-card` | `enable_server_card` | 开关为真即声明 | 空对象 |

其余开关（缓存标签、渐进发现、文件输入、触发器事件）没有任何线上标识：它们只改变本 SDK 的行为，不向对端声明任何东西。把它们称作「扩展」会在讨论协商时造成误解——对端无法从能力表里看到它们，也就不能依赖它们。

技能是唯一「声明条件比开关更严」的一个：只开开关而没注册技能、或没有资源能力，能力表里都不会出现技能键。这不是缺陷，而是「能力由注册推导」原则的直接结果（见 [/zh/learn/architecture](/zh/learn/architecture)）。

## 服务端开关族

| 开关 | 开启后的效果 | 关闭后的入口行为 | 线上标识 |
|------|-------------|-----------------|---------|
| `enable_tasks_extension` | 声明任务扩展；任务三方法与任务化的工具调用生效 | 任务方法按方法不存在拒绝 | 有 |
| `enable_skills_extension` | 满足声明条件时声明技能扩展；技能列取与目录读取生效 | 技能三方法按方法不存在拒绝 | 有 |
| `enable_apps_extension` | 声明界面扩展；`ui://` 资源读取走正常路径并校验元数据 | `ui://` 的资源读取按处理器错误拒绝，非 `ui://` 资源不受影响 | 有 |
| `enable_server_card` | 声明服务端介绍卡扩展；取卡入口返回显式卡或默认卡并校验 | 取卡入口抛处理器错误；HTTP 上的介绍卡路由另由传输侧同名开关门控 | 有 |
| `enable_etag_cache` | 列表类结果附内容哈希，命中未变更时以本地存表回退 | 结果不附哈希，条件请求不发送 | 无 |
| `enable_progressive_discovery` | 工具列表支持按查询过滤并分页 | 工具列表返回缓存全量 | 无 |
| `enable_file_input` | 工具参数里的本地与资源引用按范围切片、小文件内联；远程地址透传 | 参数原样透传 | 无 |
| `enable_triggers_events` | 触发器注册表按类型匹配，经订阅投递事件通知并回调 webhook | 发射调用直接返回，事件被丢弃 | 无 |

触发器事件的 webhook 投递自带重试（至多三次，退避递增），最终失败只记一条告警，不影响事件通知已经投递成功这一事实；这一点与其他扩展「失败即错误」的取向不同，使用时要单独考虑。

## 客户端开关族

| 开关 | 开启后的效果 | 关闭后的入口行为 | 线上标识 |
|------|-------------|-----------------|---------|
| `enable_tasks_extension` | 参与任务扩展声明；提交输入与轮询到终态的入口生效 | 上述两个入口本地抛方法不存在，其余任务入口照常发请求 | 有（需能力映射里同时给出键） |
| `enable_skills_extension` | 技能列取、单取与目录读取三个入口生效 | 三个入口本地抛方法不存在 | 有 |
| `enable_progressive_discovery` | 工具搜索请求附查询与页大小 | 仍能翻页聚合，但不附这两个参数 | 无 |
| `enable_etag_cache`（默认开） | 读取类入口附条件请求并以存表回退未变更响应 | 不附条件、不读存表，请求照常发送 | 无 |

客户端 tasks 开关的作用面比看上去小：它只挡住「提交输入」和「轮询到终态」两个入口，取任务、取消任务、把工具调用作为任务发起三处仍会发出请求。真正的兜底在应答侧——现代时代下未声明任务扩展却收到任务结果会抛处理器错误，见下一节。

## 关闭时入口返回什么

两类拒绝的含义不同，不要互换：

- **方法不存在**：这条连接上这个方法不该存在。适用于扩展开关关闭、协议时代白名单不含该方法、或方法根本没接线（工具、技能、任务类入口与未设回调的补全都走这一类，无论服务端还是客户端本地）。
- **处理器错误**：方法存在，但本次执行被拒。适用于「方法本身合法、只是这个开关决定不该碰它」的场合——`ui://` 的资源读取就是典型：资源读取在任何时代都在白名单里，关闭 apps 开关只让这一类 uri 失败。取介绍卡入口同理，而且它本来就不是线路方法，只是本地访问器。

另一类容易混淆的拒绝是**缺少必需的客户端能力**：现代时代下服务端处理任务方法时会检查对端是否声明过任务扩展，未声明即以此错误码拒绝并带上所需能力的描述；采样输入请求也走同一套检查。这不是开关关闭，而是协商缺项。

## 隐式启用路径已移除

只设任务存储不再声明任务扩展，也不再记告警；技能从来没有隐式路径。二者都必须显式置开关。选项结构体里仍留有两名「隐式启用」判定访问器，但它们已标废弃、生产代码里没有任何调用点，只是给外部调用方的兼容残留，不要据此推断行为。

## 技能：uri 形态与目录读取

技能条目的 uri 必须是 `<scheme>://<名>/SKILL.md` 形态：要求协议头非空、首段名非空、以固定文件名结尾；对具体协议头不做限制，`skill://` 只是约定而非要求。注册时形态不合或 uri 重复都会直接抛参数无效，不进入注册表。

目录读取是技能扩展声明里的一个独立标记，必须显式打开；未打开时目录读取入口回参数无效。它的作用是把技能 uri 去掉尾部文件名后当作目录前缀，列出该目录下的子项——因此目录结构完全由 uri 命名决定，而不是由另一套注册 API 决定。

技能内容是否可信不由服务端形态校验决定：限制检查、文件摘要比对、前置元数据一致性复核与授权快照复核都在客户端侧作为独立助手提供。

## 开关的生效时机

服务端与客户端都在构造时按值拷贝选项，构造完成后修改调用方手中的选项对象不再生效。缓存标签开关是唯一的例外形态：它是进程级全局状态，任一服务端实例以开启状态构造就会打开全进程的读写路径，因此同进程内多个实例无法分别取不同取值。
